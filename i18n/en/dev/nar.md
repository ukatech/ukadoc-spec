# Creating Distribution Files

*If you are using SSP 2.3.00 or later, note that the “Drop a folder to create updates2.dau or a nar” feature used on this page is unavailable unless “Enable developer features” is turned on under “General” in “Settings” → “Baseware Settings” in the owner draw (right-click menu).*

This page explains how to create distribution files (archives).

It covers creating archives not only for ghosts, but also for additional shells, balloons, and other Ukagaka/SSP-related content.

Please also read the “[Installation](../manual/install.md)” page under File Structure.

Note that this page does not explain how to create ghosts (or shells or balloons) themselves.

The instructions assume that you have already completed those steps.

## Preparing the files

First, prepare the contents to include in the archive (for a ghost, all the files that make up that ghost).

If you are developing by directly editing content installed in a baseware[※](nar.md#initial_installnarによるサイレントインストールについて), it is better to make a copy of the entire content in a separate location and use that copy as the distribution files, rather than using the installed content itself.

For information about which files are needed, refer to the “[Overall structure](../manual/directory.md)” page in the “File Structure” category of the menu on the left, as well as the pages for “[Ghosts](../manual/ghost.md),” “[Shells](../manual/shell.md),” and others.

You will prepare files such as `install.txt`, `updates2.dau`, and `developer_options.txt` later on this page, so you do not need them yet.

Next, remove files that users do not need. For example:

- Save data files for various SHIORI systems (except when needed to configure initial values, for example)
- All profile folders (these can be created in both ghost and shell folders; SSP removes them automatically)
- Development tools (such as Satorite and Reshiba, which are included with Satori)
- (MATERIA only) profile.txt in the root directory
- Configuration files generated by Windows, such as desktop.ini (SSP removes some of these automatically)
- Other development dictionary files, configuration files, log files, and so on

For SSP, you may want to configure `developer_options.txt`.

For details, see “[About developer_options.txt](nar.md#developer_optionstxtについて)” below.

## Creating the initial updates2.dau

Next, create the initial network update file (`updates2.dau`).

This mechanism detects problems such as corruption or tampering by checking whether the contents of files on the server and client differ during a network update.

Therefore, you can skip this step if you do not plan to support network updates, or if the content does not support network updates in the first place (such as [additional files for ghosts](nar.md#ゴーストへの追加ファイルについて)).

In fact, a network update file is not required in an archive.

However, creating one reduces the work the baseware has to do on the user's computer during the first network update.

Creating one is especially helpful if the archive contains many files.

First, when creating `updates2.dau` with MATERIA or CROW, you must create an empty text file named `updates2.dau` in the top-level directory in advance (for example, the directory containing the ghost folder, shell folder, and readme.txt for a ghost).

SSP creates it automatically.

Then launch the baseware and drag and drop onto it the folder containing `updates2.dau` and the files you want to update.

With MATERIA or CROW, if `install.txt` is present, archive creation takes priority and `updates2.dau` will not be created, so be sure to leave it out.

With SSP, on the other hand, if you create `install.txt` first and then drag and drop the folder, you can create `updates2.dau` and the archive at the same time.

After you drag and drop the folder, a file named `updates2.dau` should be created in the folder (or already exist), and it should contain some text.

You can open `updates2.dau` from the right-click menu or similar using a regular text editor such as Notepad, so check its contents (you do not need to understand the contents themselves).

## Preparing install.txt

Next, prepare `install.txt`, the file used to describe and configure the installation contents.

Create a text file named `install.txt` in the top-level directory (for example, for a ghost, the location containing the ghost folder, shell folder, readme.txt, and so on), and write its contents according to what you are distributing.

The contents to write vary depending on whether you want to distribute a ghost, a shell, or something else, so refer to the [Install/Update settings](../descript/install/index.md) page. Examples are also provided there.

## Creating an archive

Now we reach the archive creation stage, but by this point there is not much left to do.

This is because baseware can create an archive when you drag and drop a folder containing `install.txt` onto it.

Therefore, all you need to do is drag and drop the entire folder you have prepared onto the baseware (or onto a ghost running in it).

This should create a file named 「\[folder name\].nar[※](nar.md#initial_installnarによるサイレントインストールについて)」. This is the archive file for distribution.

All that remains is to upload this nar file to a server or file uploader, and your release is ready.

## About developer_options.txt

When creating an archive or `updates2.dau` with SSP, you can specify which files to include by creating a file named `developer_options.txt` in the top-level directory (the location where install.txt is placed when creating an archive).

For instructions and examples, see [the section about developer_options.txt on the Install/Update settings page](../descript/install/developer_options.txt/index.md).

Note that this file only takes effect when creating an archive or `updates2.dau` with SSP. It has no effect when using the [automated ghost distribution system](nar.md#ゴースト配布系自動化システムgdmについて) described below, or when creating these files with other baseware.

## About the automated ghost distribution system (GDM)

The automated ghost distribution system (GDM) is a tool that handles `updates2.dau` creation, ghost archiving, and uploading to a server in one operation.

Once installed and properly configured, it will make most of the content on this page unnecessary.

It is currently distributed by the “Maintenance Team,” as shown below.

[Automated ghost distribution system](http://ms.shillest.net/#TOOL)

For a detailed guide to installation and configuration, see the following site (the section titled “1” is not needed).

[How to use the automated ghost distribution system (GDM)](http://navy.nm.land.to/post/jidouhaihu.html)（[archive](https://web.archive.org/web/20260205013109/http://navy.nm.land.to/post/jidouhaihu.html)）

Although its name includes “ghost,” it can actually be used to create archives and upload network update files for shells, balloons, and anything else.

You can also save settings for multiple targets (such as ghost1, ghost2, shell1, shell2, shell3, balloon, and so on) for each operation, such as archive creation or network updates, then select only the operations you want to perform and run them all at once.

This is very helpful when managing a lot of content.

The initial installation and configuration take some effort, but once they are done, it is very convenient to update the network and archives for multiple pieces of content with a single click.

In addition, it completely prevents md5 mismatch errors caused by mistakes such as modifying files after creating `updates2.dau`, or uploading files with FTP transfer set to ASCII mode.

With the right settings, it is also very useful for preventing unnecessary files from being included.

As noted earlier, [developer_options.txt](nar.md#developer_optionstxtについて) is a configuration file that takes effect when creating nar archives or `updates2.dau` with SSP, so it is not relevant when creating them with GDM.

That said, GDM has its own settings for choosing which files to upload, so this file is not needed.

## About refreshinstall

If install.txt contains the following entry, the installation will be performed in a special way.

```
refresh,1
```

When this option is specified, if the installation folder already contains files, they are all deleted before installation instead of being overwritten.

Use this when, for example, changing the folder or file structure would otherwise leave unnecessary files behind.

However, note that a refresh installation also deletes *saved data and other such files*.

You can specify files to keep during a refresh installation as follows.

```
refreshundeletemask,save1.txt:save2.txt
```

For details on the format, see the [Install/Update settings](../descript/install/index.md) page as well.

## Bundling balloons and other items

You can bundle a balloon with a ghost for distribution by configuring install.txt and the file structure.

With SSP, you can also bundle plugins and headlines, as well as bundle these items with a shell instead of a ghost.

Here is an example of bundling a balloon with a ghost.

The file structure looks like this.

```filetree
+-(myghost)
　　+-install.txt
　　+-developer_options.txt (SSPのみ)
　　+-ghost
　　+-shell
　　+-(myballoon)
　　　　+-descript.txt
　　　　+-balloons0.png
　　　　:
　　　　:
```

If you write install.txt as follows, the balloon will be installed along with the ghost.

```
charset,Shift_JIS
type,ghost
name,ゴースト名
directory,myghost（※ゴーストのフォルダ名。英数）
balloon.directory,myballoon（※バルーンのフォルダ名。英数）
```

An install.txt file is not needed on the balloon side<br />
※If present, it will be ignored. You may include one in case you also want to distribute it separately.

If the balloon folder name after installation differs from its name in the distribution, use the following.

```
charset,Shift_JIS
type,ghost
name,ゴースト名
directory,myghost（※ゴーストのフォルダ名。英数）
balloon.directory,hoge_balloon（※インストール後のバルーンフォルダ名。英数）
balloon.source.directory,myballoon（※アーカイブ内のバルーンフォルダ名。英数）
```

The balloon folder named myballoon in the example above will then be named<br />
hoge_balloon after installation.

Set refresh for bundled files as follows.

```
balloon.refresh,1
balloon.refreshundeletemask,hoge.png:huga.txt:...
```

To bundle something other than a balloon (SSP only), replace the “balloon” part of entries such as “balloon.directory,” “balloon.source.directiory,” and “balloon.refresh” with the relevant item, that is, one of

- headline
- plugin
- calendar.skin
- calendar.plugin

Then bundle the files in the same way as the balloon in the example above.

## About Additional Files for Ghosts

To create an archive of additional files (a supplement) for a ghost, preserve the ghost's original folder structure and include only the files you want to add.

For example, to add a file named "dic_supplement.txt" to ghost/master, the structure is as follows.

```filetree
+-(mysupplement)
　　+-install.txt
　　+-developer_options.txt (SSPのみ)
　　+-ghost
　　　　+-master
　　　　　　+-dic_supplement.txt
```

The contents of install.txt for this archive are as follows.

```
charset,Shift_JIS
name,追加トークパッチ
type,supplement
accept,対象ゴーストの本体側名
```

## Packages for Multiple Installations

This method is for SSP only.

You can create a package that installs multiple items at once by creating an archive with the following file structure.

```filetree
+-(mypackage)
　　+-install.txt (package用)
　　+-(myghost1)
　　　　+-install.txt (myghost1用)
　　　　+-developer_options.txt (SSPのみ)
　　　　+-ghost
　　　　+-shell
　　　　:
　　+-(myghost2)
　　　　+-install.txt (myghost2用)
　　　　+-developer_options.txt (SSPのみ)
　　　　+-ghost
　　　　+-shell
　　　　:
```

Prepare a package-level `install.txt` in the folder, and place each item inside that folder.

Each item has its own *individual install.txt* and follows a normal installation structure that can also be archived on its own.

It may help to think of this as “packing” multiple items into folders and adding a separate package-level `install.txt` as the label on the box.

Write the package-level install.txt in the top-level folder as follows.

```
charset,Shift_JIS
type,package
name,パッケージ名
```

Write each individual install.txt as usual (see [Install/Update settings](../descript/install/index.md), for example).

If you use [developer_options.txt](nar.md#developer_optionstxtについて), note that you should put it in *each item's folder*, not in the top-level folder.

The example above contains two ghosts, but you can include any content that is valid as an archive, not just ghosts.

However, be careful not to combine items with different targets when they specify an accept value, such as type,shell or type,supplement.

## Silent Installation Using initial_install.nar

When SSP starts with a nar file named `initial_install.nar` in the same folder as ssp.exe, that nar file is automatically installed with overwrite at startup, without a confirmation dialog.

After installation is complete, `initial_install.nar` is automatically deleted.

This feature is mainly for developers, and is useful when distributing a package that includes ghosts or other items with SSP.

For example, to create a distribution package that includes a specific ghost alongside SSP, simply place `initial_install.nar` alongside ssp.exe. The ghost will be installed automatically when the user starts SSP for the first time.

**対応:** SSP 2.7.52

!!! tip "Tip"

    - **[※1 Baseware](nar.md#ファイルの準備)**: Software such as SSP, MATERIA (the original Ukagaka), and CROW that provides the foundation for running ghosts.
