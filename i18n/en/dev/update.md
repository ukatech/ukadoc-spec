# Support for network updates

*For SSP 2.3.00 and later, note that the “Drop a folder to create updates2.dau” feature used on this page is unavailable unless “Enable developer features” under “General” in “Settings” → “Baseware settings”, accessed from the owner draw (right-click menu), is turned on.*

This page explains the settings and preparations required to support network updates.

In addition to ghosts, SSP can also perform network updates for shells, balloons, plugins, and headline sensors; this page covers those as well.

## Prepare a server

First, prepare a server for network updates.

A free hosting server of the kind used for personal websites will do.

Depending on its restrictions and settings, a hosting server may cause problems with network updates (especially free services).

Pay particular attention to the following:

- You can upload files with the required extensions.
- Advertisements are not automatically added to text files.

The following page should be helpful if you are looking for a free hosting server.

[Da-Debe Wiki: Where should I distribute my ghost? (free hosting edition)](http://emily.shillest.net/specwiki/index.php?%E7%A5%9E%E5%A4%9C%E3%81%BF%E3%82%85%E3%82%93%2F%E3%82%B4%E3%83%BC%E3%82%B9%E3%83%88%E9%85%8D%E5%B8%83%E3%81%99%E3%82%8B%E3%81%AA%E3%82%89) (external site)

## Set the update URL

In general, this is specified in `descript.txt`.

Add a line like the following to `descript.txt` to set it.

```
homeurl,http://xxx.yyy/myghost/
```

The URL specified here is the network URL of the folder containing the files for the network update (the location where you will later create `updates2.dau`).

The exact URL depends on the server. Suppose the server's root directory is http://xxx.yyy/ and the folder for the ghost to be updated over the network (myghost) is located on the server as follows:

```filetree
+-root
　　+-ukagaka
　　　　+-myghost1
　　　　　　+-ghost
　　　　　　+-shell
　　　　　　+-readme.txt
　　　　　　+-updates2.dau
+-index.html
+-hogehoge.html
+-style.css
:
:
```

If it is placed in this layout, then in descript.txt:

```
homeurl,http://xxx.yyy/ukagaka/myghost1/
```

Write it like this.

For ghosts, in addition to specifying the URL in `descript.txt`, you can also specify a URL for [homeurl](../list/shiori-resource/ghost/homeurl.md) in [SHIORI Resource](../list/shiori-resource/index.md).

The method for specifying homeurl through SHIORI Resource on the ghost side depends on the SHIORI, so it is not covered here. Refer to the documentation for the relevant SHIORI.

## Remove unnecessary files

Next, remove files that users do not need. For example:

- Save data files for various SHIORI implementations (except when needed for default settings, etc.)
- All profile folders (created in both ghost and shell; SSP removes them automatically)
- Development tools (such as Satorite and Resibah, included with Satori)
- (MATERIA only) profile.txt in the directory root
- Configuration files generated by Windows, such as desktop.ini (SSP removes some of these automatically)
- Other development dictionaries, configuration files, logs, and similar files

With SSP, `developer_options.txt` can help if removing these files manually one by one is troublesome.

For details, read [the explanation below](update.md#developer_optionstxtについて).

What should you do if you have already updated with one of these *unnecessary files included*, or if a file you *used previously has become unnecessary* (for example, because you renamed it) as you continue to release updates?

In these cases, *simply deleting the unnecessary file from the server will not delete the file on the user's side*.

This is because a network update overwrites files on the user's side with files from the server; it does not synchronize (mirror) the files.

Use `delete.txt` to remove files that have already been distributed through a network update.

Place `delete.txt` in the top-level folder containing the files for the network update (for example, for a ghost, the folder containing the ghost and shell folders and `readme.txt`; for other items, the folder containing descript.txt).

For an example layout, see “[Network update](../manual/update.md)” under File structure in the menu on the left.

## Creating updates2.dau

Next, create the network update file (`updates2.dau`).

This mechanism detects problems such as corruption or tampering by checking whether the contents of files on the server and client sides differ.

To create `updates2.dau` with MATERIA or CROW, you must first create an empty text file named `updates2.dau` in the top-level directory (for example, for a ghost, the directory containing the ghost folder, shell folder, readme.txt, and so on).

SSP creates it automatically.

Then start the baseware[※](update.md#dauがサーバに弾かれてしまう場合について), and drag and drop onto it the folder containing `updates2.dau` and the files you want to update.

With MATERIA or CROW, if `install.txt` is present, creating a nar file takes priority, so `updates2.dau` will not be created. Be careful not to include it.

After you drag and drop the folder, a file named `updates2.dau` should be created in the folder (or already exist), and something should be written in it.

You can open `updates2.dau` with a regular text editor such as Notepad by right-clicking it or using another method, so check its contents (you do not need to understand what they mean).

## Uploading to the server

Once you have reached this point, all that remains is to upload the files to the server using FTP software or similar.

However, be sure to set the transfer mode to *upload all files in binary mode*.

Uploading in ASCII mode will cause the network update to fail.

It is safest to keep a copy of the version “before the network update” in your local baseware, then confirm that the network update completes successfully after uploading.

## About developer_options.txt

When SSP creates an archive or `updates2.dau`, you can specify which files to include by placing a file named `developer_options.txt` in the top-level directory (the location where install.txt is placed when creating an archive).

For instructions and examples, see [the section on developer_options.txt on the Install/Update settings page](../descript/install/developer_options.txt/index.md).

Note that this file only takes effect when SSP creates an archive or `updates2.dau`. It has no effect when using the [ghost distribution automation system](update.md#ゴースト配布系自動化システムgdmについて) described below, or when creating them with other baseware.

## About the ghost distribution automation system (GDM)

The ghost distribution automation system (GDM) is a utility that handles creating `updates2.dau`, archiving ghosts, and uploading them to a server, all in one operation.

Once installed and properly configured, most of the content on this page will no longer be needed.

It is currently distributed by the “Maintenance Team,” as described below.

[Ghost Distribution Automation System](http://ms.shillest.net/#TOOL)

For a more detailed guide to installation and configuration, refer to the following site (the content of “1” is not needed).

[How to use the Ghost Distribution Automation System (GDM)](http://navy.nm.land.to/post/jidouhaihu.html) ([Archive](https://web.archive.org/web/20260205013109/http://navy.nm.land.to/post/jidouhaihu.html))

Although “ghost” appears in its name, it can actually be used to create archives and upload network update files for shells, balloons, and anything else.

You can also save settings for operations such as archive creation and network updates for multiple targets (such as ghost 1, ghost 2, shell 1, shell 2, shell 3, balloon, and so on), then select and run only the operations you want at any given time, all at once.

This is very helpful when managing a lot of content.

The initial installation and configuration take a bit of work, but once they are done, it is very convenient to update network files and archives for multiple pieces of content with a single click.

It also completely prevents md5 mismatch errors caused by mistakes such as modifying files after creating `updates2.dau`, or uploading files with FTP set to ASCII mode.

Of course, with appropriate configuration, it is also very useful for preventing unnecessary files from being included.

Note that [developer_options.txt](update.md#developer_optionstxtについて), mentioned above, is a configuration file that takes effect when creating nar files or `updates2.dau` using SSP, so it is not relevant when creating them with GDM.

In any case, GDM has its own settings for which files to upload and which not to upload, so this file is unnecessary.

## If the server rejects ".dau" files

Depending on the rental server settings, it may not handle files with the unfamiliar “.dau” extension.

In that case, you can use `updates.txt` instead.

To use it, replace every occurrence of “`updates2.dau`” on this page with “`updates.txt`”.
